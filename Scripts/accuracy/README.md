# Event accuracy investigation

**Current production status:** see [the integration acceptance record](../../PRODUCTION-INTEGRATION.md).
The shipping engine and paired observation path now pass the original 36-event
gate. The sections below describe the preserved initial investigation; their
statements about isolated candidates and pending integration are historical.

This is the executable investigation for AstrologyKit's `B369-ASTRONOMY-60S`
blocker. The original full VSOP87B + 77-term IAU2000B experiment fails one frozen
event. A [follow-up JPL audit and UTC experiment](FOLLOWUP.md) identifies a
concrete route forward and passes all 36 unchanged events diagnostically. All candidate code is isolated here; it is not compiled into AstronomyKit.
Production, dependency pins, and numerical goldens remain unchanged.

The 24 `fixtures/A*.json` files are byte-for-byte copies from AstrologyKit commit
`85f2d440f231902581dd40726e19072c6fe832a9`. `fixtures/provenance.json` records
their original location and SHA-256 hashes. These are public development cases,
not an untouched evaluation set. No reference event is generated from AstronomyKit.

## Run

Python 3.10+ and clang are required. No Python dependencies are needed for the
model matrix. Run these commands from the AstronomyKit package root:

```sh
python3 Scripts/generate-models.py --check
python3 -m unittest discover -s Scripts/accuracy -p 'test_*.py' -v
python3 Scripts/accuracy/measure.py --output .build/accuracy
```

The final command builds four optimized, isolated native libraries: baseline,
full planetary series, full nutation, and both. It measures 30 planetary/lunar
events. Six house/angle events additionally require built AstrologyKit Swift
objects. To reproduce all 36 events on macOS, run `swift build` in an unchanged
AstrologyKit checkout at the reference revision, then supply its actual products
and CLibAstronomy module-map paths:

```sh
python3 Scripts/accuracy/measure.py --output .build/accuracy \
  --products /absolute/path/to/AstrologyKit/.build/out/Products/Debug \
  --module-map /absolute/path/to/AstrologyKit/.build/checkouts/AstronomyKit/Sources/CLibAstronomy/module.modulemap \
  --require-pass
```

These paths reflect Xcode-backed SwiftPM; other build layouts need their
equivalent object/module paths. The driver records object and module-map hashes.
It relinks the compiled Swift observations against each C model. The `date`
variant substitutes a true-ecliptic-of-date planetary rotation in the diagnostic
only; it is not an implemented downstream migration. The baseline also runs
the unchanged fixed-obliquity production conversion.

`--require-pass` deliberately exits nonzero while any full-candidate event
misses the 60-second gate, misses the separate convergence gates, or the full
36-event production comparison is absent. The ordinary command emits diagnostic
results without asserting acceptance. Missing files, invalid hashes, non-finite
samples and unbracketed roots are errors, never clean empty results.

## Component attribution

Use a separate environment for the exact frozen oracle package; Swiss Ephemeris
is not a shipping dependency. The component tool requires the previously built
full-model library (`.so` on Linux):

```sh
python3.11 -m venv .build/accuracy/oracle-env
.build/accuracy/oracle-env/bin/pip install pyswisseph==2.10.3.2
.build/accuracy/oracle-env/bin/python Scripts/accuracy/components.py \
  .build/accuracy/full.dylib .build/accuracy/components.json
ASTRONOMY_ACCURACY_LIBRARY=.build/accuracy/full.dylib \
  python3 -m unittest discover -s Scripts/accuracy -p 'test_*.py' -v
```

The optional native-library unit test checks the full nutation against ERFA's independently
published reference. Without a compiled library it is explicitly skipped.

The component report compares each engine's native UT conversion, common TT,
apparent coordinates, light-time-only coordinates, geometric coordinates, and
heliocentric coordinates. Common-TT comparisons evaluate Swiss at the native
model's TT at every sample. They do not overwrite only the reception epoch of a
light-travel calculation. Station comparisons use Swiss's returned `SPEED`, as
the frozen oracle does. A separate width sweep differentiates Swiss longitudes
to expose the difference between these two methods without changing references.

## Model provenance and limits

`Scripts/model-data/manifest.json` pins the same upstream Astronomy Engine commit
already vendored by the package. The full source tables and generated headers
are committed. `python3 Scripts/generate-models.py` regenerates them offline;
`--check` verifies both source hashes and generated bytes. The generator preserves
every coefficient and time power, including the series used for state derivatives.
The nutation implementation retains all 77 terms and the fixed planetary offsets.

`models.py` applies only those two substitutions to the pinned baseline C source.
It retains the existing Moon, Pluto, aberration, light-travel and delta-T paths,
as well as deterministic math and concurrency/range protections. There is no
runtime model selector or public API addition.

The bisection probes search around known ordinary roots. They neither discover
all events in a query nor prove completeness, tangencies, or causal ordering.
The wider 1900–2100 campaign, JPL cross-checks, platform release matrix,
performance qualification, major release, and paired AstrologyKit migration
remain pending production integration and acceptance. See `ACCURACY-INVESTIGATION.md` for the
results and the decision needed to resume.
