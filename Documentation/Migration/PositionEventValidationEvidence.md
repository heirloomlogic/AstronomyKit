# Finite position and event validation evidence

The first independently referenced public-API batch covers 7,511 position comparisons and 233 matched events across the approved 1900–2130 TT interval. Every sampled direction was below the owner-approved one-arcminute limit. The current implementation exceeded the strict 60-second target for seven lunar apsides and eleven Pluto alignments nominally; one of those Pluto rows and one Neptune alignment remain inconclusive under the frozen one-second numerical allowance. These are finite numerical observations, not continuous or physical-uncertainty qualification.

The [approved requirements](approved-accuracy-targets.json), [frozen position/lunar plan](position-event-sampling-plan.json), [separate geometric-event plan](geometric-event-sampling-plan.json), [implementation plan](PositionEventValidationPlan.md), [reference conventions](PositionEventReferenceConventions.md), and [independent date-plane review](DatePlaneReferenceReview.md) define the scope. Raw NASA/JPL Horizons responses and response/query/plan hashes are retained under `Scripts/reference-data/sources/position-events/` and `sources/geometric-events/`. There are 329 query/response pairs. The astronomical engine and historical source fixtures were not changed. The public-API runner uses an isolated scratch package to preserve the existing migration runner and its frozen source hash.

## Positions and reported ranges

The position schedule has 131 characterization and 128 disjoint holdout dates, including the opening endpoint, final second of 2130, and J2000 in characterization. Holdout excludes the old distance archive dates. Twenty-nine explicitly named series cover all eleven approved bodies: nine simultaneous heliocentric vectors and ten geocentric bodies under both `.none` and the public default aberration flag. The Moon uses geometric reference vectors for either flag, matching its actual public implementation. The phases contain 3,799 and 3,712 comparisons respectively. The [full assessment](position-event-assessment.json) records all rows, summaries, source ephemerides, input hashes, executable identity and toolchain provenance.

The largest raw angular difference was 0.196925 arcminute (11.8155 arcseconds), for geocentric Pluto. No angular limit was widened after measurement. Raw differences retain J2000/FK5-versus-ICRF orientation, outer-planet body-center approximation, fixed-heliocentric Sun-origin motion, and approximate default aberration. Especially for `LT+S`, these remain deliberately named physical-reference diagnostics rather than an exact correction-parity claim. No certified source covariance or continuous error bound is supplied.

The 19 heliocentric/geocentric-`.none` series also provide 4,921 fresh nominal radius comparisons under the revised body-specific distance limits. None exceeded its limit. This is a separate set of vector-derived radius diagnostics; the earlier `fresh-distance-sampling-plan.json` was not acquired or replaced. The original historical characterization/holdout budgets remain unchanged.

All 1,938 nominal distance exceedances in the wider 29-series report belong to the public default geocentric vectors. Their model backdates the observer as an aberration approximation, changing the vector norm; Horizons `LT+S` treats stellar aberration as a direction correction. For example, the largest default Mars radius difference was 100.965 ppm, while its `.none` maximum was 0.8473 ppm. Do not silently apply the `.none` distance acceptance to default corrected vector lengths or call either correction path equivalent to the other. A corrected direction and a physically defined reported range need separate evaluation in any repair.

## Event timing, identity and direction

The lunar apsis pilot independently scans geometric Earth-center/Moon-center range rate in 16 predetermined 31-day windows, including opening, J2000, 2101 and closing coverage. The extension uses those original windows for geometric lunar nodes and nine predetermined full calendar years for eight planets' heliocentric alignments: 1900, 1930, 1960, 1990, 2020, 2050, 2080, 2101 and 2130. These event pilots are fixed finite surveys, not a newly qualified event holdout or a complete interval event census.

All planned windows/cases were evaluated, including zero-event alignment windows. No event-count, identity, order or direction failure occurred. The [lunar assessment](position-event-assessment.json) and [geometric assessment](geometric-event-assessment.json) retain every matched event and every uncertainty classification. The worst lunar residual was perigee on 2067-11-14 TT, about 189.7 seconds early. The angular position requirement cannot itself establish the event-time requirement: slowly changing event observables can turn small trajectory errors into several minutes of timing error.

Reference roots are discovered from independent coarse grids, then refined from directly queried fine states under fixed schedules. Four-point cubic interpolation must be strictly monotonic within the root bracket; a single sampled sign change does not suffice. Quadratic comparison is a numerical convergence diagnostic. The one-second numerical allowance was fixed before event acquisition and remains unchanged. It is an engineering stability allowance, not an astronomical covariance or proof that no roots were missed between samples. Exactly 60 seconds fails; an envelope reaching that threshold remains inconclusive.

The [same-model lunar search diagnosis](lunar-event-search-diagnosis.json), bound to its [frozen diagnostic plan](lunar-event-search-diagnosis-plan.json), bisects the norm of public lunar vectors using three explicit-TT central stencils for every matched apsis. The maximum shift from the public search result was 0.621 second; all three stencil widths retained the same seven independent timing exceedances. This supports the lunar model as the dominant limitation in these cases rather than search tolerance. It is a same-model numerical diagnosis, not independent lunar accuracy evidence.

## Lunar repair feasibility

A [retrospective lunar candidate probe](lunar-ephemeris-candidate-probe.json), governed by its [premeasurement plan](lunar-candidate-probe-plan.json), evaluates the official `de440s.bsp` Moon-center and Earth-center segments: `(3,301) − (3,399)`. Explicit TT is converted to approximate geocentric TDB with the pinned ERFA evaluator. The independent Horizons archive returned DE441 for the Moon. This compares different numerical ephemeris solutions, which share observational inputs; it is not independent observational proof.

The candidate's worst sampled angular difference was 0.000137891 arcminute and its maximum radius difference was 0.00262918 ppm across 259 Moon positions. All 73 previously archived lunar apsides/nodes were within 0.014611 second of their references. These cases were already observed when selecting the candidate, so this is feasibility evidence, not a fresh candidate holdout or production acceptance. It supports retaining the strict event target while investigating a model repair.

The complete downloaded kernel is 32,726,016 bytes (31.21 MiB); a development-only Moon/Earth excerpt over the required interval with guards is 13,902,896 bytes (13.26 MiB). These are file sizes, not app installation/download size, Swift resident memory or runtime cost. The kernel's [official segment inventory](https://naif.jpl.nasa.gov/pub/naif/generic_kernels/spk/planets/aa_summaries.txt) establishes those body identities and coverage. [NAIF redistribution rules](https://naif.jpl.nasa.gov/naif/rules.html) and provenance/attribution requirements still need shipping review; this work selects no distribution or production replacement.

The prototype does not repair Pluto. The short planetary kernel contains Pluto-system barycenter `9`, which cannot silently replace the body-center `999` contract. A Pluto repair needs an explicit center-offset model or another qualified body-center source. See [candidate source research](AccuracyModelCandidates.md).

A separate [native representation probe](native-lunar-candidate-probe.json), governed by its [frozen plan](native-lunar-probe-plan.json), confirms that both excerpt segments share the same coefficient grid and type/frame. Subtracting corresponding Float64 coefficients produces a geometric Moon-center-minus-Earth-center payload of 6,581,696 bytes (6.28 MiB). This is a custom development format, not a SPK kernel or a shipped package resource. The standalone optimized Swift evaluator uses analytic Chebyshev derivatives and read-only memory mapping, consistent with the [SPK type-2 polynomial definition](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/req/spk.html#Type%202:%20Chebyshev%20(position%20only)).

Native parity covers 42,521 states: all 332 archived lunar position/event epochs, 21,094 retained record boundaries, 21,093 midpoints and two excerpt guards. The maximum component differences from the original full-kernel evaluator were 2.91e-10 km for position and 5.82e-11 km/day for derivatives, below the frozen 1e-7 limits. This qualifies the sampled evaluator/representation parity only; it does not add independent astronomical observations or a new candidate holdout. A synthetic split-date control caught a native precision loss and passed after keeping the two TDB parts separate through record selection; limits were not widened. Independent review then found a malformed tiny-interval payload could trap on an unrepresentable integer quotient. A sixth control reproduced the crash and passed after rejecting nonfinite/unrepresentable quotients and guarding index arithmetic; the real four-day data was unaffected.

Five local warm sequential one-million-state trials recorded a median 118 nanoseconds per position-and-velocity state and 1.18 milliseconds for mapping/header/full finite-coefficient validation. Total peak process RSS was 12,468,224–12,484,608 bytes (about 11.9 MiB), versus 5,881,856–5,914,624 bytes for separate no-data baseline processes. The median peak difference was 6,586,368 bytes (about 6.28 MiB); this is descriptive separate-process evidence, not an exact allocation or app resident-memory attribution. The microbenchmark excludes JSON I/O, TT-to-TDB conversion, date-frame transforms, event search, mixed workloads, concurrency and device/Linux behavior; it cannot satisfy #83 performance gates.

## Verification and remaining work

Fault tests cover angular unit/axis/sign errors and invalid vectors; strict event boundaries; ambiguous cubic roots; wrong target/time/frame/correction/site/date population; detached public request identity/epoch/window/order; reference dependencies loaded outside the pinned environment; and attribution to a different executable. Independent reviews identified material gaps in those controls and candidate helper-source provenance; the fixes were applied without changing limits, public model outputs or raw reference data.

Local checks passed: 87 reference-data Python tests, 20 migration foundation tests, 14 migration comparison tests, and 706 Swift tests across 187 suites with the pre-existing known polar issue. Both new Swift executables passed explicit strict formatting lint, and the 925-discovered-test contract inventory matched current sources; that inventory count is not an execution count. Offline report checks replay the separately built public runner and retain astronomical pass/fail summaries. The original migration runner and root package manifest remain unchanged, preserving their frozen archive binding. The source/oracle lock check passed, but its recorded compiler environment differs from the current compiler; no recorded-environment binary parity is claimed. Hosted CI, Linux/device integration, full performance gates and release qualification were not performed. The resume ledger records exact final check results.

Remaining families include default-corrected stations, apparent geocentric pair events, planetary apsides, seasons, rise/set and tangencies, eclipse/transit contacts and peaks, and local observer circumstances. Their observables, correction/frame alignment, Earth-rotation/atmosphere/radius conventions and source uncertainty still require separate frozen acceptance work. Existing polar diagnostics do not become a whole-domain rise/set pass. Neither #81, #83 nor #124 is closed by this pilot.

The owner authorized independent progress. After presenting the new model-architecture choice, the development-only investigation continued with bundled lunar data as a provisional direction; no production replacement was selected. The candidate and native probes make that direction credible. Fresh candidate holdout, native API/time/frame integration, shipping resources and licensing, mixed-workload/platform costs and broader event qualification remain required before a model cutover. Pluto still needs a separate body-center repair.
