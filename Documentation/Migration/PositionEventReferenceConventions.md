# Position and event reference conventions

This research note supports the [approved qualification plan](AccuracyQualificationPlan.md): all calendar years 1900–2130 in TT, angular position at most one arcminute, and each comparable event strictly less than 60 seconds from its reference with correct existence, identity and direction. It does not change production, old fixtures, their allowances, or accepted limits. Recommendations below concern finite qualification against a pinned numerical ephemeris; no whole-interval or observed-event accuracy pass is claimed.

## Source requests and identities

Use the [Horizons API](https://ssd-api.jpl.nasa.gov/doc/horizons.html) with `EPHEM_TYPE='VECTORS'`, `TIME_TYPE='TT'`, `TLIST_TYPE='JD'`, `REF_SYSTEM='ICRF'`, `REF_PLANE='FRAME'`, `OUT_UNITS='AU-D'`, `VEC_TABLE='2'`, and `CSV_FORMAT='YES'`. Supply explicit numeric Julian dates in `TLIST`; omit start/stop/step parameters in that mode. Set `VEC_CORR` independently for each observable. These controls select states in equatorial ICRF axes rather than silently adopting a fixed ecliptic plane. Preserve complete requests, responses and hashes; validate the JSON error field and returned metadata, not merely HTTP success.

The [Horizons manual](https://ssd.jpl.nasa.gov/horizons/manual.html#time) explicitly supports TT vectors; its API summary has inconsistent shorthand. Require returned `JDTT`. TDB differs periodically from TT by at most 0.002 seconds. Convert an epoch or retain that mismatch; relabeling a TDB number does neither.

Use Sun center `500@10` for heliocentric vectors and Earth center `500@399` for geocentric vectors. [Horizons object selection](https://ssd.jpl.nasa.gov/horizons/manual.html#select) assigns body centers Mercury `199`, Venus `299`, Earth `399`, Mars `499`, Jupiter `599`, Saturn `699`, Uranus `799`, Neptune `899`, Pluto `999`, Moon `301`, Sun `10`; `1`–`9` are system barycenters, with `3` the Earth–Moon barycenter. Keep these identities fixed rather than choosing the better-fitting center after examining residuals.

Pin the actual source tags in each response. A planetary barycenter ephemeris does not by itself provide every planet center; the earlier [candidate research](AccuracyModelCandidates.md) records this distinction. The [official time-span page](https://ssd.jpl.nasa.gov/horizons/time_spans.html) describes available spans in TDB, so check each selected target/center pair and guard epochs needed by stencils or light-time iteration. Availability is distinct from accuracy.

On 2026-10-03, a two-row availability probe for `COMMAND='301'`, `CENTER='500@399'`, `VEC_CORR='NONE'` with the settings above returned Moon/Earth `{source: DE441}`, ICRF, `JDTT`, and the requested calendar labels at JD `2415020.5` (1900-01-01 00:00:00 TT) and `2499391.499988426` (2130-12-31 23:59:59 TT). The response signature was NASA/JPL Horizons API version `1.2`; the documentation describes version `1.3`. Neither version should replace the other in provenance. This small live probe was not archived as an acceptance fixture and establishes neither every body's coverage nor angular/event accuracy. The required calendar interval is `[2415020.5, 2499391.5)` TT; its closing boundary is 2131-01-01, not an included epoch.

## Geometric and received-light vectors

The [NAIF aberration definitions](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/req/abcorr.html) distinguish simultaneous geometry `T(t)-O(t)` from reception geometry `T(t-lightTime)-O(t)`, expressed in barycentric positions. `NONE` returns geometry; `LT` includes reception light time; stellar aberration is additional. NAIF's SPICE `LT` uses one iteration, while `CN` converges. Those implementation details belong to SPICE and must not be assumed to describe Horizons merely because correction names resemble each other. NAIF also warns that its corrections do not include the relativistic corrections required at highest precision.

The following mapping comes from the public [position API](../../Sources/AstronomyKit/Position.swift) and its actual [C implementation](../../Sources/CLibAstronomy/astronomy.c), rather than treating all functions called apparent as identical.

| Public observable | Independent source candidate | Equivalence and retained limitation |
| --- | --- | --- |
| `heliocentricPosition(at:)` | Same-TT Sun-center `NONE` vectors | Matches simultaneous origin and correction convention. Local VSOP rotation produces an EQJ/FK5-related orientation; ICRF frame alignment remains separate. |
| Moon `geocentricPosition(at:aberration:)` | Earth-center Moon `NONE` | Moon bypasses light-time and aberration for either flag. This matches geometric center separation, not a received-light lunar direction. |
| Planet/Sun `geocentricPosition(... .none)` | Earth-center `LT`, or explicitly bridged geometric barycentric states | Local target is backdated while Earth's heliocentric position stays at reception. Direct JPL `LT` retains the Sun-origin-motion mismatch described below. |
| Planet/Sun `geocentricPosition(... .corrected)` | JPL `LT+S` as an explicitly unmatched diagnostic | Local observer is also backdated as an aberration approximation. It is not an exact stellar-aberration rotation and can change the vector norm. |
| `geocentricEclipticState(at:aberration:)` | Same source candidate as its position, followed by a declared date-frame transform | Its position repeats the geocentric-vector/ecliptic path. Rates include light-time and date-frame derivatives; Moon rates use a finite difference. A source position match does not automatically qualify rates. |

For `.none`, the local vector is `Phelio(s)-Ehelio(t)`, whereas barycentric reception geometry is `Pbary(s)-Ebary(t)`. Their difference includes the Sun's motion between emission `s` and reception `t`. The [existing reference conventions](DistanceReferenceConventions.md) already separate this approximation from model residuals. For a model-only angular diagnosis, construct the local heliocentric-origin convention from independent barycentric geometric states at both epochs, solving emission time independently. For an observed-direction claim, retain the full barycentric reference and quantify the approximation. These answer different questions and must be separate report columns.

For geometric angular residuals, retain vector lengths separately and compare normalized directions with a stable great-circle calculation, such as `atan2(norm(cross(u,v)), dot(u,v))`. Also report wrapped longitude and latitude residuals for spherical API fields under the frozen metric. Component, radius and direction agreement are different observations. Longitude is undefined for a vector on the coordinate pole; invalid or singular cases require explicit reporting rather than an invented angle.

## Date frames and event definitions

Local `Astronomy_Ecliptic` applies precession, nutation and true obliquity to EQJ vectors. Its nutation code uses the full 77-term IAU2000B series; [the C source](../../Sources/CLibAstronomy/astronomy.c) is the exact implementation contract. A reference transform needs independent review and a pinned definition. The official [SOFA release](https://www.iausofa.org/current-software) provides IAU precession/nutation algorithms, but substituting a SOFA realization does not automatically reproduce every local frame-bias, precession, nutation or rounded-matrix choice.

An algebraic consequence of the local `nutation_rot` matrix is useful: converting mean ecliptic coordinates to mean equatorial coordinates, adding nutation, then rotating back using true obliquity reduces to a rotation about the mean ecliptic pole by nutation in longitude. Consequently, that common longitude-origin rotation cancels in a same-epoch longitude difference and preserves ecliptic latitude. It does not cancel from an absolute longitude or its time derivative. This is an implementation-derived inference, not a claim that independently named date frames always coincide. Confirm the reduction with reviewed matrix tests when building the reference evaluator.

The [Horizons observer definitions](https://ssd.jpl.nasa.gov/horizons/manual.html#obsquan) call quantity 31 an IAU76/80 ecliptic-of-date apparent direction including light-time, gravitational deflection and stellar aberration. `AIRLESS` removes refraction only. Quantity 18 evaluates heliocentric longitude at emission, not the requested simultaneous epoch. Neither is a shortcut to every local event definition.

| Event family | Actual local/public residual | Independent common-TT root and status |
| --- | --- | --- |
| `searchRelativeLongitude`, `searchOpposition`, `searchSuperiorConjunction` | `direction*(Earth heliocentric longitude - planet heliocentric longitude) - target`; direction is `+1` for outer planets, `-1` for Mercury/Venus; target `0` or `180` for the convenience searches | Root simultaneous Sun-center `NONE` vectors transformed into the declared date plane. Common longitude-origin nutation cancels. This is tractable after frame and body-center controls. Geocentric apparent planet–Sun roots are a distinct diagnostic. |
| Geocentric longitude conjunction/opposition using `pairLongitude` | Longitude of body 1 minus body 2, both local `NO_ABERRATION`, then the date transform; Moon remains geometric | Root independent source vectors under those correction/origin conventions. JPL quantity 31 pairs can supply another explicitly apparent definition, but cannot silently qualify this function. Classify inferior/superior planet conjunction using geometry as well as longitude. |
| Longitude stations of `geocentricEclipticState` | Zero of the selected API's longitude rate, in its moving date frame, with the declared aberration flag | Root an independently differentiated position function at explicit TT. Include frame motion. A derivative of fixed-ICRF longitude, or a daily longitude increment, defines a different event. No dedicated public station search was found; qualify the state-derived event and the external root solver separately. |
| Lunar perigee/apogee | Extremum of instantaneous center–Earth geometric lunar range; public search uses a central distance-slope stencil of total width `0.001` day | Root `dot(r,v)=0` from Earth-center Moon `NONE` states, or bracket range extrema using independent position samples. Classify minimum versus maximum. This is the first recommended pilot because radial extrema avoid the date-frame and apparent-direction ambiguities. Measure the public finite-stencil offset rather than assuming its search is an exact continuous derivative root. |
| Lunar ascending/descending nodes | Zero of `Astronomy_EclipticGeoMoon(...).lat`, geometric Moon in the date ecliptic; ascending means south-to-north | Root geometric `NONE` lunar latitude using a declared date-plane transform and classify the crossing direction. The common longitude-origin rotation preserves latitude, so the local nutation reduction simplifies this family. Fixed J2000 `z=0`, osculating-element node longitude, or apparent quantity 31 latitude are different definitions. |
| Solar longitude/seasons | `Sun.eclipticState` and the solar longitude search follow `Astronomy_SunPosition`, including a fixed one-AU backdate and a frame evaluated at that adjusted time | Retain an explicitly separate reference definition and measure the fixed-delay/frame approximation. Do not substitute the general geocentric Sun state or quantity 31 without checking these differences. |

The search mappings are directly inspectable in [RelativeLongitude.swift](../../Sources/AstronomyKit/RelativeLongitude.swift), `rlon_offset`, `Astronomy_PairLongitude`, `moon_distance_slope`, `Astronomy_SearchLunarApsis`, `MoonNodeSearchFunc`, and `Astronomy_SearchMoonNode` in [astronomy.c](../../Sources/CLibAstronomy/astronomy.c). In particular, opposition does not mean an independently searched minimum distance or maximum brightness; those extrema need their own definitions.

For a station reference based on transformed states, write `q(t)=R(t)r(t)` and use `qdot=Rdot*r+R*rdot`, followed by `longitudeRate=(qx*qdoty-qy*qdotx)/(qx*qx+qy*qy)`. Alternatively differentiate independently sampled longitude with phase unwrapping and a shrinking explicit-TT stencil. These are proposed evaluator equations, not a new source derivative contract. [Existing range-rate evidence](RangeRateEvidence.md) shows why Horizons light-time vector velocities cannot simply inherit SPICE derivative semantics. Use position stencils or an independently verified velocity convention for received-light roots; geometric apsis roots avoid that unresolved issue.

## Finite root and uncertainty controls

1. Freeze requests, target IDs, event equations, corrections, date-frame transform, epoch/stencil schedules, event pairing rules and difficult geometries before evaluating acceptance residuals. Retain endpoints and predetermined near-boundary samples, including 2101–2130 and Pluto interpolation transitions. The existing three-date and daily-Mercury archive is not this acceptance set.
2. Construct local evaluations from explicit TT using `AstroTime(tt:deltaTModel:)`; compare reported event `terrestrialTime` against JDTT roots in seconds. Public `addingDays` and C searches advance UT and derive TT through their captured Delta T model. Record that model and test its boundary behavior; do not treat a UT step as an exact TT step or convert through future civil UTC for these dynamical events. See [Time.swift](../../Sources/AstronomyKit/Time.swift) and `Astronomy_AddDays` in the [C source](../../Sources/CLibAstronomy/astronomy.c).
3. Independently bracket each reference root, record endpoint signs and final width, and refine until the numerical time envelope is small relative to 60 seconds. Reevaluate direct source positions near the root; interpolation from a coarse acquisition must have its own assessed error. Step/stencil halving and alternate interpolation expose instability but alone do not prove a continuous enclosure or an event was never missed.
4. Record source output rounding, epoch representation, solver width, interpolation/stencil sensitivity and convention-alignment allocations separately. Convert angular residual uncertainty to time only with a justified local nonzero slope; station timing instead needs the slope of longitude rate. Near a tangent or flat root, simple angle/speed estimates become ill-conditioned. Retain such cases for tighter reference work, not automatic acceptance or limit growth.
5. For a reference time interval `[a,b]`, strict acceptance requires `max(abs(local-a), abs(local-b)) < 60 seconds` after all adopted reference allowances. A nominal difference below 60 with an uncertainty interval reaching that boundary does not establish the strict result. An engineering stability allowance is not a published ephemeris covariance, and printed digits do not establish physical accuracy.
6. Match event counts, identities, ordering and direction independently of time error. Include starts exactly at and just around a reference event, 0/360-degree wrap, inferior versus superior conjunction, ascending versus descending nodes, and minimum versus maximum apsides. A nearby but wrong event fails even when its timestamp is close. A finite coarse scan plus refinement is sampled evidence until completeness is separately justified.

## Recommended next scope and retained gaps

Start with common-TT geometric position comparisons and lunar apsis roots, then simultaneous heliocentric relative-longitude roots and geometric lunar nodes after reviewing the date-plane transform. This order isolates trajectory residuals before adding received-light, aberration and moving-frame derivative conventions. Keep geocentric pair events, default corrected stations and solar absolute-longitude events as separately named next pilots; their apparent-source comparisons can be acquired as diagnostics while alignment remains explicit.

This note does not qualify rise/set, polar crossings, horizon tangencies, altitude extrema/transits, elongation extrema, magnitude extrema, planetary apsides, eclipse peaks/contacts/classification, occultations, Mercury/Venus transit contacts, or local observer circumstances. They remain required event families under the approved plan, with separate geometry, observer, limb-radius, atmosphere, Earth-orientation and source-uncertainty work as applicable. [Polar-source research](PolarSunriseReferenceSources.md) remains relevant to #124; nothing here closes that known archive failure or changes its allowance. Small bodies, stars and Galilean-moon events also lack a complete required-interval qualification here; no new unsupported-domain pass is implied.

No acceptance acquisition, event residual report, production change, performance qualification, hosted CI or independent implementation review was performed for this note. The small Moon request establishes the feasibility of explicit-TT source access only. The current public solar model remains unchanged.
