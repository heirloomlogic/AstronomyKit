# Distance reference conventions

This note fixes the observable distinctions needed for a finite 1900–2100 characterization. It supplements [the literature review](DistanceAccuracyLiterature.md); it does not establish a continuous accuracy guarantee or a published kilometre tolerance. The local implementation observations below refer to `Sources/CLibAstronomy/astronomy.c` and the hash-bound archive in `Scripts/model-data/manifest.json`.

## Reference requests and time

Use numeric Julian days, explicit `TIME_TYPE='TT'`, `REF_SYSTEM='ICRF'`, `REF_PLANE='FRAME'`, `OUT_UNITS='AU-D'`, and `VEC_TABLE='3'`. Archive the request, full response, SHA-256, returned target identity, source ephemeris, time scale, center, and correction settings. The [Horizons API parameter reference](https://ssd-api.jpl.nasa.gov/doc/horizons.html) defines the frame, units, correction modes, and vector table fields; response validation must reject missing or contradictory metadata rather than silently accept defaults.

The [live Horizons manual, Specification of Time](https://ssd.jpl.nasa.gov/horizons/manual.html#time), permits TT vector tables, although the API summary table still lists only TDB or UT for vectors. Confirm the returned JDTT header in each response. Local `CalcVsop` consumes `time.tt / 365250`; the archived authors' notice specifies dynamical time `TAI + 32.184 s`, so direct TT comparison avoids a model-dependent UT/Delta-T conversion. For a TDB fixture instead, transform its epoch explicitly or record a time-scale allowance; TT and TDB differ periodically by at most 0.002 seconds according to that manual. Do not label an unchanged TDB number TT.

Horizons presently documents DE441 for planetary barycenters, Sun, Moon, Mercury, Venus, and Earth; other planet centers use satellite solutions. Pin the actual returned source tags, not an assumed DE440 label. [Park et al. (2021)](https://ssd.jpl.nasa.gov/doc/Park.2021.AJ.DE440.pdf) explains the distinct DE440/DE441 fits and reference-frame alignment; those reference-fit residuals are not AstronomyKit error bounds.

## Centers and frames

Use Sun center `500@10` for heliocentric quantities and Earth center `500@399` for geocentric quantities. The API's public center-of-body contract maps Mercury, Venus, Earth, Mars, Jupiter, Saturn, Uranus, Neptune, Moon, and Pluto to `199`, `299`, `399`, `499`, `599`, `699`, `799`, `899`, `301`, and `999`. Horizons IDs `1`–`9` select system barycenters; `3` selects EMB. [Horizons object selection](https://ssd.jpl.nasa.gov/horizons/manual.html#select) distinguishes these entities.

Raw `VSOP87B.ear` is **Earth**, not EMB. The authors' [1988 paper, Table 1 and section 4.1](https://articles.adsabs.harvard.edu/pdf/1988A%26A...202..309B), distinguishes the main VSOP87 EMB solution from the derived Earth solution and explains the ELP2000-82 lunar correction. The [CDS catalog](https://cdsarc.cds.unistra.fr/viz-bin/ReadMe/VI/81?format=html&tex=true) and local archive header identify the B series as heliocentric spherical variables in the dynamical J2000 ecliptic. Local `HelioVectorUnguarded(BODY_EARTH)` returns that series directly; `BODY_EMB` adds the local geocentric Moon vector divided by `1 + EARTH_MOON_MASS_RATIO`. Subtracting a second lunar offset from Earth would introduce a center error.

The reviewed VSOP sources label the outer planets but do not explicitly settle their satellite-system center convention. Local `CalcVsop` applies no satellite-center offset, while `Astronomy_HelioVector` promises body centers. Retain body-center requests for that public behavior; optional barycenter requests are separate diagnostics. Do not choose a different target after seeing which residual is smaller. Resolve any center offset explicitly before claiming a convention-matched theory comparison. The Pluto integrator likewise has no explicit Pluto/Charon center-offset model.

Local `VsopRotate` uses the authors' published dynamical-ecliptic-to-FK5 matrix, reproduced in `Scripts/model-data/vsop87.txt`; it is not merely a J2000 obliquity rotation. Horizons ICRF and FK5/J2000 differ slightly, as the [manual's Reference Frames section](https://ssd.jpl.nasa.gov/horizons/manual.html#frames) explains. Record that frame difference as a vector-comparison limitation or apply an independently specified frame transformation. A common exact rotation preserves heliocentric radius and geocentric range; it does not preserve a comparison of unmatched vector components. The local rounded matrix adds a separate tiny numerical effect.

## Three distinct distance observables

For geometric heliocentric radius and vector residuals, request `VEC_CORR='NONE'` and compare `Astronomy_HelioDistance` and `Astronomy_HelioVector` at the same TT epoch. Report absolute radius error and the norm of the three-component vector error separately. Radius agreement cannot establish vector agreement or an Earth-relative range limit.

For planetary received-light range, request geocentric `VEC_CORR='LT'` and compare the norm of `Astronomy_GeoVector(..., NO_ABERRATION)`. Local `BodyPosition` freezes Earth at reception and iterates the target's emission time. This is closer to the received-light observable but retains a heliocentric-origin approximation: `Phelio(s) - Ehelio(t)` differs from `Pbary(s) - Ebary(t)` by the Sun's barycentric motion between emission `s` and reception `t`. Characterize or allocate that approximation separately. The [NAIF light-time formulation](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/cspice/spkez_c.html) defines the barycentric reception equation.

`ABERRATION` is a distinct diagnostic: local `BodyPosition` backdates Earth as well as the target, so its norm can change. It is not equivalent to applying a stellar-aberration rotation to the received-light vector. NAIF's [stellar-aberration description](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/cspice/spkez_c.html) describes such a rotation, which preserves norm. An empirical limit for `NO_ABERRATION` range must not silently become a limit for the public default `ABERRATION` result.

For the Moon, `Astronomy_GeoVector` bypasses backdating and calls `Astronomy_GeoMoon` regardless of the aberration flag. Compare its distance with geocentric `NONE`, explicitly named geometric lunar range. HelioVector(Moon) adds that instantaneous lunar vector to the Earth model. A lunar received-light test would need a separate implementation or a quantified approximation allowance.

## Empirical budget policy

The owner-selected policy uses a 2× characterization margin, followed by evaluation on disjoint held-out epochs. The implemented rule in [DistanceAccuracyEvidence.md](DistanceAccuracyEvidence.md) also uses approximate literature scales as engineering floors and adds separate approximation and alignment allocations. Fix the interval, epoch-generation rules, body IDs, correction modes, comparison observables, and separate implementation allowances before running characterization. Freeze the resulting budgets and their input hashes before evaluating the holdout. Keep all bodies, including Moon and Pluto, separate; a held-out exceedance fails the policy and must not trigger automatic threshold growth.

Report sample counts, endpoint inclusion, worst epoch, maximum and distribution of residuals, and holdout results per observable. Retain a sampled characterization maximum as evidence; do not call twice that value a scientific guarantee or an interval certificate. A global grid can miss orbital extrema, lunar periodic structure, and polynomial/integrator boundaries, so include predetermined phase-offset and boundary samples without using acceptance residuals to choose their locations.

The local Moon is Brown-derived rather than VSOP87; Pluto uses custom gravity integration and cached interpolation rather than TOP2013 itself. Their provenance and lack of transferable radial limits are documented in [the literature review](DistanceAccuracyLiterature.md). Neither the VSOP distance-scale table nor an angular accuracy statement supplies their kilometre budget. Full-series versus polynomial checks establish implementation agreement with the selected model, while independent Horizons residuals characterize that model plus any explicitly retained convention approximations.
